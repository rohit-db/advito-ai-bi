Reference Architecture

White-label analytics,
powered by Databricks.

APEX is a reference app showing that Databricks is all you need to build customer-facing analytical applications — embedded AI/BI dashboards, an agentic “Ask” experience, governed metrics, per-tenant data isolation, and your own identity layer, with no third-party BI tool.

📊 Embedded AI/BI 🤖 Genie MCP 🔐 Per-tenant isolation ☁️ Deploy anywhere

The system at a glance

A React frontend and a FastAPI backend sit between your users and the Databricks workspace. The backend authenticates to Databricks as a Service Principal — so end users never see a Databricks login. Everything below is either the app you deploy (indigo) or native Databricks capabilities (amber/green) it orchestrates.

White-label authentication

APEX is its own identity provider: users sign in on a branded login page with email and password, receive an HMAC-signed session cookie, and never see a Databricks login. The cookie carries tenant_id — the join key that selects the per-tenant Service Principal for Genie and dashboard embeds. 

sequenceDiagram
    autonumber
    participant User as 👤 Client User
    participant Login as FastAPI /login
    participant Dir as User directory
    participant Gate as Session gate
    participant DBX as Databricks

    User->>Login: POST email + password
    Login->>Dir: verify password hash (PBKDF2)
    Dir-->>Login: tenant · tenant_id · role
    Login-->>User: Set-Cookie apex_session (HMAC-signed)

    User->>Gate: request with cookie
    Gate->>Gate: verify signature + expiry
    Gate->>Login: resolve tenant SP from tenant_id
    Login->>DBX: embed / Genie as tenant SP
    DBX-->>User: scoped data (UC row filter)
Login → signed cookie → middleware → tenant SP. Users live in Lakebase (prod) or a JSON file (demo); tenant_id joins directly to apex_client_registry.
No Databricks login for end users. The app authenticates to Databricks as a Service Principal on their behalf. Operators (role = operator, tenant_id = *) bypass tenant scoping and can manage SPs from the Admin page. Set AUTH_ENABLED=true in production; it is off by default so local dev works without a login gate.

White-label dashboard embedding

Dashboards embed with a Service-Principal-scoped token (no Databricks login), the SDK's hideDatabricksLogo flag, and the documented f_… URL params for filters. The SDK has no filter API yet, so the app rebuilds the embed URL itself and re-applies the logo config after each reload. 

sequenceDiagram
    autonumber
    participant UI as React UI
    participant BE as FastAPI /api/embed/token
    participant SP as Tenant Service Principal
    participant DB as Databricks OAuth
    participant IF as Embed iframe

    UI->>BE: request embed token (dashboard id)
    BE->>SP: resolve tenant SP creds
    BE->>DB: 3-step OAuth exchange (authorize, token, scoped)
    DB-->>BE: scoped CAN_RUN embed token
    BE-->>UI: token
    UI->>IF: load embed URL with token hash + f_ filter params
    Note over IF: SDK config hides logo, CSS crops page header
    UI->>IF: on filter or page change, rebuild URL (keeps filters + logo)
Token mint runs as the tenant SP, so the embed is scoped to that tenant's data by the UC row filter.
Why rebuild the URL? Native SDK filter passing is on the roadmap (DB-I-14988). Until then, we keep the SDK for auth, token-refresh, and logo-hiding, and apply filters via the documented f_<field> URL params — a fully supported path today.

Ask APEX — agentic Q&A via Genie MCP

“Ask APEX” talks to the managed Genie MCP server (Genie One MCP). The backend streams the model's reasoning, generated SQL, result tables, tool calls, and deep links back to the browser over Server-Sent Events — Agent mode, out of the box, today. 

sequenceDiagram
    autonumber
    participant UI as React UI (Ask APEX)
    participant BE as FastAPI /api/genie-mcp
    participant MCP as Managed Genie MCP
    participant GS as Genie Space + Metric View

    UI->>BE: POST question (SSE opens)
    BE->>MCP: connect as tenant SP, discover tools
    MCP->>GS: run tool, MEASURE() SQL
    GS-->>MCP: rows + SQL + metadata
    MCP-->>BE: stream reasoning, tool calls, results
    BE-->>UI: SSE reasoning, SQL, table, deep links
    Note over UI: renders live, history saved to Lakebase
The same MCP path powers the per-dashboard Executive Summary using a preset prompt (Overview · KPIs · Strategic Insights).

Multi-tenant data isolation

Each tenant gets its own Service Principal. Both Genie and the dashboards run as that SP, and a Unity Catalog row filter is the load-bearing control — isolation is enforced in the data plane, not the app code. The app can never accidentally leak another tenant's rows.

🧑‍💼

Operator Admin page

Create / rotate / deactivate tenant SPs, and a “Manage access” dialog to grant or revoke per-resource CAN_RUN — all audited.

🔒

Secrets, encrypted

SP client secrets are AES-GCM encrypted in Lakebase and only ever returned once, at onboard or rotate.

🪶

Fail-soft by design

Before any tenant is onboarded — or with Lakebase off — the app degrades gracefully to the app SP and JSON/in-memory stores.

Deploy anywhere — no Databricks App required

The same FastAPI + React app runs on the Databricks Apps platform or fully externally (EC2 / ECS / any Docker host), reaching Databricks purely via a Service Principal (M2M). Embedding, Genie MCP, auth, and isolation behave identically in both.

One codebase, one auth path (Service Principal). Packaged with a Dockerfile + docker-compose for external hosting.
  1. Data plane — Unity Catalog metric view over your governed source table, with a row filter for tenant isolation.
  2. Auth — app authenticates as a Service Principal; end users sign in through the white-label login (or SSO at your edge).
  3. Runtime — FastAPI serves the built React bundle and the /api/* routes (embed tokens, Genie MCP SSE, persistence).
  4. Persistence — Lakebase (managed Postgres) stores conversation history, filter prefs, and the tenant/SP registry.
